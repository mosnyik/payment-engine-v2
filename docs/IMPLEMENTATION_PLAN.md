# Payment Rail v2 — Implementation Plan

> **Resuming in a new session?** Read this file top to bottom — every phase is marked ✅ if done, and each section ends with a `*Next: ...*` line. Then run `git log --oneline -10` and `go test ./...` (against the externally-connected dev Postgres configured in `.env` — no local container to start) to confirm the working tree matches what's documented here before continuing. `ARCHITECTURE.md` has every design decision behind these choices — check it before re-deciding something that's already settled.

Status: living doc. Companion to `ARCHITECTURE.md` (design decisions, module map, ledger schema, session state machine) — this doc is about *build order and sequencing*, not design. Update as phases complete or sequencing changes.

## How this is organized

Distinct buildable parts, grouped into: the foundation layer everything depends on, the nine business modules from the module map, and cross-cutting ops tooling — ordered by dependency, with one deliberate sequencing call-out (Phase 4).

## Phase 0 — Foundation ✅ complete

Nothing else can start without this. No business functionality yet.

- ✅ **`platform/db`** — Postgres connection pooling (`pgx`), `golang-migrate` setup, base migration tooling. Verified against a live local Postgres (Docker, port 5433 to avoid a conflicting native install).
- ✅ **`platform/gateway`** — tenant HMAC+API key authentication: signature covers method+path+timestamp+body-hash, constant-time compare, 5-min replay window. mTLS deliberately deferred — it needs a tenant record to say which tenants use it, which doesn't exist until Phase 2; the router's shape doesn't change when it's added. Routing via `chi`.
- ✅ **`platform/admin-auth`** — separate credential space for staff: bcrypt-hashed passwords, sessions looked up by token hash (no secret-comparison step at all, sidestepping timing attacks structurally rather than via constant-time compare), login-timing normalized against user enumeration, full audit log table. Direct replacement for v1's single shared `ADMIN_SECRET`.
- ✅ **`platform/eventbus`** — `outbox_events` table, dispatcher claims one row per transaction via `SELECT ... FOR UPDATE SKIP LOCKED` (isolates a failing handler to its own event, not the whole batch), immediate wake-up + poll-interval backstop. Verified: successful dispatch marks `dispatched_at`; a failing handler rolls back cleanly and redelivers next tick.
- ✅ **`platform/idempotency`** — inbound-request idempotency store, scoped per-tenant (`(tenant_id, key)`, not a bare key — two tenants can pick the same client-supplied string safely). Three-outcome model (`Claimed`/`InFlight`/`Completed`) verified against the live DB.
- ✅ **`platform/config`** — the single place secrets and operational settings are loaded and validated at startup. `main.go` calls `config.LoadEnv()` once; nothing else reads `os.Getenv` directly. Source is an interface (`EnvSource` today; a Vault/AWS-Secrets-Manager-backed `Source` later needs no changes anywhere else). Validates required fields, rejects the local-dev `DATABASE_URL` when `APP_ENV=production`, and collects every problem in one error rather than failing one at a time. The three operational constants that were hardcoded in gateway/adminauth/eventbus (`HMAC_CLOCK_SKEW`, `ADMIN_SESSION_TTL`, `EVENTBUS_BATCH_SIZE`) now flow through here too, with defaults matching the old hardcoded values.

All five have integration tests passing against a live Postgres instance (`go test ./...` from the repo root).

## Phase 1 — Ledger ✅ complete

- ✅ `ledger_accounts`, `ledger_transactions`, `ledger_entries`, `ledger_balances` (see `ARCHITECTURE.md` §6 for schema). `tenant_id` has no FK yet — the `tenants` table doesn't exist until Phase 2; add the constraint then rather than stub a placeholder table now. Uses `UNIQUE NULLS NOT DISTINCT` on accounts so platform-level (tenant_id NULL) accounts correctly dedupe — a plain `UNIQUE` would treat every NULL as distinct and silently allow duplicates.
- ✅ `internal/ledger.Post()` — the single write path. Enforces balance-per-asset (not just overall), rejects zero/negative amounts, and claims the idempotency key atomically (`ON CONFLICT ... DO NOTHING` + `ErrAlreadyPosted`) before any entry is written, all inside one DB transaction.
- ✅ `decimal.Decimal` (shopspring) used throughout, never `float64` — registered as a native pgx type in `platform/db` so it works as both scan target and query param with no manual string conversion.
- ✅ Verified with the exact worked example from `ARCHITECTURE.md` §6 (100 USDT-TRC20 → NGN, full deposit→fx→settlement→sweep flow) end to end against a live DB, asserting every final account balance. Also verified: unbalanced entries rejected (both single-asset and the cross-asset case where two different assets individually don't balance), duplicate idempotency key rejected without double-applying the balance change, and `GetOrCreateAccount` correctly dedupes platform-level accounts.

Everything downstream posts through this — it needs to exist and be trustworthy before anything else that moves value.

## Phase 2 — Tenant, Corridor, Compliance ✅ complete

- ✅ **`corridor`** — config entity binding asset+network × fiat currency to provider bindings (priority-ordered for failover), limits, Travel Rule thresholds, `compliance_hold_timeout` (default 24h, overridable per corridor). Upsert-by-natural-key throughout.
- ✅ **`tenant`** — profile, fee schedule (with per-corridor override), corridor entitlements, credential storage. Satisfies `gateway.CredentialLookup` (compile-time-asserted and runtime-tested). Added `platform/crypto` (AES-256-GCM) along the way — an HMAC secret can't be one-way hashed like a password, so it needed at-rest encryption instead of plaintext; documented as an interim measure until a real KMS exists. Closed the `ledger_accounts.tenant_id` FK gap flagged back in Phase 1. SSRF-validated webhook URLs (rejects non-https and loopback/private/link-local resolved addresses, tested against the real AWS metadata IP) — direct fix for the matching v1 audit finding.
- ✅ **`compliance`** — KYB case flow, manual-hold queue, provider registry scaffold (`Registry`/`ScreeningProvider`, empty by default — no vendor selected yet). Transaction-screening routing and Travel Rule volume aggregates deliberately **not** built — no real caller exists until the `session` module (Phase 5); building them now would be speculative.
- ✅ **Onboarding workflow** — wired as real HTTP endpoints (not just a Store-level test): `POST /admin/login`, `/admin/tenants`, `/admin/tenants/{id}/kyb`, `/admin/compliance/holds`, `/admin/compliance/holds/{id}/resolve`, `/admin/tenants/{id}/api-keys`, `/admin/tenants/{id}/corridors/{id}`, `/admin/tenants/{id}/webhook`, all gated by `platform/admin-auth`. `cmd/server` now actually listens on a port for the first time — previously it only connected to the DB and ran migrations. Along the way, `gateway.NewRouter`'s protected route group was found to be unreachable from outside the package (a real gap, not by design) and fixed to return the sub-router so other packages can mount authenticated routes on it — proven with a `/v1/ping` smoke route hit by an actually-issued tenant credential, not a synthetic one.
- The **Phase 2 acceptance test** (`cmd/server/onboarding_test.go`) drives the full sequence over real HTTP: register → submit KYB (falls into hold, no vendor configured) → appears in the ops queue → resolved by an admin → tenant activates → credential issuance refused-then-allowed → corridor entitlement → webhook SSRF rejection-then-acceptance → the issued credential successfully authenticates on a real protected route, and is confirmed rejected without credentials and rejected using an admin token (proving the two auth surfaces are genuinely separate, not just differently labeled).

## Phase 3 — Rate engine ✅ complete

Ported from v1 (see `ARCHITECTURE.md` §7): provider adapters, background fetch job, aggregator (system-rate-as-ceiling selection rule), `LockRate()`, plus the new `rate_locks` table (not in v1). Depends only on `corridor` (active-currency list) and the foundation.

- ✅ **`internal/rate`** — `system_rates` (ops-configured ceiling, keyed per fiat currency — not a single hardcoded-NGN row like v1), `provider_rates` (background-cached external quotes), `rate_locks` (persisted lock, adaptation #3). `Provider`/`LiveFetcher` interfaces split reading a cached quote (transaction path) from making the real HTTP call (background job only) — mirrors v1's `RateProvider`/`HttpRateProvider` split. `systemProvider` always enabled; `busha`/`liquidramp`/`anchor` ported as the same TODO-endpoint stubs v1 shipped with, disabled by default via config (`BUSHA_RATE_ENABLED` etc.) until a real integration is supplied.
- ✅ **`corridor.ListActiveFiatCurrencies`** — adaptation #2: the fetch job polls this instead of a hardcoded `['NGN']`.
- ✅ **`FetchJob`** — ticker-driven (default 30s, `RATE_FETCH_INTERVAL`), skips starting entirely if no external provider is enabled (matches v1), wired into `cmd/server/main.go` as a background goroutine.
- ✅ **`LockRate()`** — selects the lowest quote among enabled providers (system rate as ceiling), applies the 1% slippage buffer, prices the crypto asset in USD (CoinMarketCap, USDT hardcoded to 1 — same known gap as v1: no fallback provider for asset pricing, revisit post-pilot), and persists the result to `rate_locks`.
- No HTTP routes yet — same state as `corridor`: config/Store-level only. Nothing calls `LockRate()` until Phase 5's session module exists; `internal/rate/rate_test.go` exercises the Store directly against a live Postgres.

*Next: Phase 4 — Treasury is ✅ complete (Busha adapter + self-custody HD wallets). Phase 5 — Session is next.*

## Phase 4 — Treasury ✅ complete *(sequencing call, not strict dependency order)*

The highest-stakes module — self-custody HD wallets, KMS-backed key encryption, per-chain watchers, per-asset sweep policy — is also the most complex and, per the v1 audit, the most consequence-heavy if built wrong.

**Build the partner-custodied adapter (Busha) first.** It's simpler (no HD derivation, no KMS integration, no watcher/sweep policy to get right) and the SLA already exists. This gets a working end-to-end pilot (collection → settlement) running fastest, while self-custody gets the time and scrutiny it deserves without blocking everything else behind it.

1. ✅ **`treasury` — Busha (partner-custodied) collection provider adapter.** `treasury_address_reservations`/`treasury_deposits`/`treasury_custody_balances` tables; `CollectionProvider` interface + Busha adapter built the same TODO-stub way rate's Busha/LiquidRamp/Anchor adapters were (real endpoint/response shape/webhook signature scheme unknown — v1 never actually built this integration either, so there was nothing to port). `ReserveAddress`/`GetDepositInstructions` fail over across a corridor's active collection-provider bindings by priority; `HandleDepositWebhook` does signature-verified, compare-and-set (`pending`→`detected`→`confirmed`) deposit-state transitions, idempotent on `(reservation_id, tx_reference)`. Same "config/Store-level only" precedent as `rate`/`corridor` — no HTTP routes wired yet, nothing calls `GetDepositInstructions()` until `session` (Phase 5) exists. Verified against a live Postgres (`go test ./internal/treasury/...`).
2. ✅ **`treasury` — self-custody HD wallet manager, per-chain watchers, confirmation policy, sweep execution.** All four launch chains (BTC, ETH, BNB, TRX + USDT variants) in one pass, per v1 precedent — unlike Busha, v1's self-custody flow (HD wallet + watchers + sweeper) was real, working code, genuinely ported rather than designed from scratch.
   - **`internal/treasury/wallet`** — BIP39/BIP32 HD derivation (BIP84 for BTC, BIP44 for ETH/BSC/Tron; BSC deliberately shares ETH's derivation/address format), using lightweight primitives (`btcsuite/btcd` family, `tyler-smith/go-bip39`) rather than pulling in go-ethereum — except `fbsobreira/gotron-sdk` for Tron specifically (protobuf tx format; hand-rolling that correctness-critical encoding was judged riskier than the dependency weight, which transitively pulls in go-ethereum anyway via Tron's own signing helper). EIP-1559 RLP encoding is hand-rolled and verified two ways: a from-scratch decoder proving encode/decode round-trips, and signature-recovery proving a produced signature recovers the signer's own address. BTC sweep signing is verified by running the produced witness through `txscript`'s real script-execution engine, not just "no error." A separate HD account index funds gas top-ups, deliberately not sharing the deposit-address account namespace the way v1's merchant-funding wallets did.
   - **Key storage fixes v1's exact audit gap** (lesson 2, seed ciphertext + key colocated in one `.env`): ciphertext lives in a new `hd_wallet_seed` DB row (provisioned once via `adminctl -init-wallet`, mnemonic printed exactly once), key lives in config (`HD_WALLET_SEED_ENCRYPTION_KEY`), same interim `config.Source` seam already used for `TenantSecretEncryptionKey`.
   - **Address reuse fixes v1's exact audit gap** (lesson 3, app-level check-then-insert let one deposit fund two sessions): a partial unique index (`treasury_address_reservations(address) WHERE status='reserved'`) makes a second open reservation on one address a DB constraint violation, not a race an app check can lose.
   - **Watchers** poll only currently-open self-custody reservations (on-demand, like v1 — never a global chain scan) against real, live-verified API shapes: Blockstream (BTC), Etherscan V2 unified API (ETH/BSC, native + ERC20/BEP20 USDT), TronGrid (TRX, native + TRC20 USDT). A shared `recordDepositTransition` helper (factored out of the Busha webhook handler) means both the webhook path and the watcher path drive the same compare-and-set deposit state machine.
   - **Sweep**: volatile assets (BTC/ETH/BNB/TRX) sweep immediately on confirmation, triggered inline from the watcher; stable assets (USDT-*) batch on a configurable balance threshold or time backstop — a v2-only refinement, confirmed absent from v1, which sweeps everything immediately. `treasury_sweeps` is the outbound-transaction audit trail; sweep destinations are DB-configured (`SetSweepDestination`), not hardcoded.
   - All bookkeeping/policy logic and the wallet package's crypto are covered by tests verified against a live Postgres; the full chain-broadcast paths (UTXO fetch → sign → broadcast, gas top-up sequencing) are implemented using the same verified signing primitives but have **not** been exercised against real funded testnet/mainnet addresses — that's a manual, ops-supervised step outside automated CI.

## Phase 5 — Session ✅ complete

The orchestrator: `corridor` → `compliance.ScreenSession()` → `rate.LockRate()` → `treasury.GetDepositInstructions()`, the state machine, and TTL/SLA behavior. Depended on all of Phases 2–4, so naturally last among the "input" modules.

Grounding this phase in the actual code (not just `ARCHITECTURE.md` §8's design) surfaced three gaps closed as part of this build, not assumed away:

- ✅ **`compliance.ScreenSession()`** — didn't exist before this phase (only KYB's `ScreenTenant` did). Same shape as `ScreenTenant` (falls to the manual hold queue with no provider registered), plus two session-specific adaptations: a rolling Travel Rule check (sums `fiat_amount` directly off the `sessions` table for the tenant within the corridor's `travel_rule_window` — no separate aggregates table) that forces a hold regardless of what a provider would decide, and `hold_expires_at` populated from the corridor's `compliance_hold_timeout` (KYB holds leave it null; session holds need a real TTL for the TTL job below to act on).
- ✅ **The eventbus dispatcher turned on for real** — `main.go` never called `bus.Run(...)` before this phase, and no module anywhere called `Publish`. `session` is the first real consumer: `EventbusPollInterval` added to config, `bus.Run` started alongside the rate fetch job and the new TTL job.
- ✅ **`treasury` now publishes `treasury.deposit_detected`/`treasury.deposit_confirmed`** — `recordDepositTransition` (webhook.go) previously wrote to `treasury_deposits` via two separate un-transacted calls; refactored to run in one transaction that also publishes (only on a real transition, never on a redelivered/duplicate webhook) via a nil-safe `bus` field + `SetEventBus` setter (same optional-dependency convention as `tenantWebhooks`), so every existing treasury test is unaffected.
- ✅ **`internal/session`** — `Store.CreateSession` runs corridor lookup → entitlement check → `ScreenSession()` → (approved: `LockRate()` + `GetDepositInstructions()` → `pending`, publishing `session.created`; hold → `compliance_hold`; rejected → `rejected`), all CAS transitions (`UPDATE ... WHERE status = <expected>`) copying `treasury.recordDepositTransition`'s pattern. `RegisterEventHandlers` subscribes to the two treasury events above to drive `pending → deposit_detected → deposit_confirmed`, publishing `session.*` in turn — `deposit_confirmed` is the fan-out point, left as a bare publish since `settlement` (Phase 6) doesn't exist yet, same "config/Store-level only, no caller yet" precedent used for `rate`/`corridor`/Busha in earlier phases.
- ✅ **`ResolveComplianceHold`** — the state machine's `compliance_hold → pending`/`rejected` "analyst approves/rejects" transitions weren't reachable through anything except the TTL job's own timeout path once first drafted; added as the admin-facing counterpart (`POST /admin/sessions/{sessionID}/resolve`), reusing `transitionToPending`/`transitionToRejected` with the expected prior status parameterized so both the initial screening decision and a later hold resolution share one code path.
- ✅ **TTL/SLA background job** (`internal/session/ttl.go`) — implements `ARCHITECTURE.md` §8 exactly: fixed 30-minute expiry for pre-deposit `screening`/`pending` sessions (`SessionTTL`, a compiled-in design constant like `rate.slippageBuffer`, not an ops knob); `compliance_hold` expiry keyed on the case's own corridor-configured `hold_expires_at` instead (a hold review legitimately outlives 30 minutes); `sla_breached_at` set once for everything else still in flight, without ever touching `status` — a session with a deposit already detected keeps progressing normally after breaching.
- ✅ **`POST /v2/sessions` / `GET /v2/sessions/{id}`** — the tenant-facing HTTP surface, gateway-HMAC-gated. The response shape deliberately omits `compliance_case_id` (§5: never leak the specific screening reason to the client); `GET` on another tenant's session returns 404, not 403, so existence isn't confirmed either way.

Verified against a live Postgres: full `go test ./...`, including the state machine's happy/hold/rejected paths, the deposit-event pipeline via a real dispatched `eventbus.Bus`, CAS/race and out-of-order-event safety, all three TTL/SLA rules, and an HTTP acceptance test (`cmd/server/session_test.go`) driving session creation → hold resolution → deposit events end to end through the real router, mirroring `onboarding_test.go`'s style for Phase 2.

## Phase 6 — Settlement ✅ complete

Grounding this phase in the actual code surfaced two facts that shaped the build directly: `ledger.Post()` had never been called by any production code path before this phase (Phases 1–5 built and tested it in isolation), and `eventbus.Handler`'s doc comment ("a handler that needs to make a slow or external call... should instead write local state a dedicated worker picks up") is a hard constraint — `ledger.Post()` always opens its own transaction, so it can never run inside a `bus.Subscribe` handler.

- ✅ **`internal/settlement`** — the ledger-claim-then-dispatch pipeline. `session.deposit_confirmed`'s subscriber (`events.go`) does nothing but claim a local `settlements` row (`pending_dispatch`) per the eventbus constraint above; a ticker-driven `DispatchWorker` (`dispatch.go`, ARCHITECTURE.md §5's "config/Store-level only" precedent doesn't apply here — this is the first phase whose background worker *is* the primary write path, not session/rate's HTTP-triggered one) does the real work: posts the previously-deferred `deposit_confirmed`/`fx_conversion` ledger transactions, transitions session to `settling`, then claims `settlement_payout:session_X:attempt_N` (the ledger's atomic pre-dispatch claim, §6) before ever calling the provider.
- ✅ **Five named settlement provider adapters** — cNGN, Flutterwave, Paystack, Monnify, Hydrogen Pay, all TODO-stub (disabled by default, no real partner chosen yet), sharing one `httpSettlementProvider` struct + per-provider closures (`providers.go`) — mirrors `internal/rate/providers.go`'s multi-provider pattern rather than treasury's single-adapter (`bushaProvider`) shape, since settlement needed several named candidates from the start, not one placeholder.
- ✅ **The full 4-bucket retry policy** (§8) — bucket 1 (rejected before acceptance) and bucket 2 (webhook-reported async failure) share one retry/failover routine (`handleAttemptFailure`), preferring an untried provider before retrying the same one, backing off `RetryBackoff` (~60s) when none is available, capped at `MaxAutoRetryAttempts` (3); bucket 3 (confirmation timeout) is detected by a separate `TimeoutJob` that only sets `ops_paged_at`, never touches `status` (§8: "stays settling"); bucket 4 (terminal rejection) fails immediately, no retry. Every failed attempt posts a compensating `settlement_reversal:session_X:attempt_N` before the next attempt claims a fresh key — verified against the exact ledger arithmetic (a "failed" attempt's reversal restores the `tenant_payable` liability, it doesn't zero it — the payout never actually went out).
- ✅ **Signature-verified webhook handling** (`webhook.go`) — `payout.succeeded`/`payout.failed`/`payout.returned`, same `ComputeWebhookSignature`/`VerifyWebhookSignature` HMAC-SHA256 shape `treasury`'s webhook handling established, CAS-transition-then-publish (`transitionSettlementAndPublish`) mirroring `session.transitionToPending`'s begin/update/publish/commit pattern. `payout.returned` (a post-`settled` reversal) reopens the `tenant_payable` liability without ever touching the crypto side (§8 rule 6) and opens a `settlement_reversals` ops case.
- ✅ **Ops-facing surface** (`ops.go`, `cmd/server/settlement_handlers.go`) — `GET /admin/settlements`, `POST /admin/settlements/{id}/retry` (the human-confirms-bucket-3 path shares one method with settlement_failed's ops-triggered retry, per §8: "same shared policy, not two"), `POST /admin/settlements/reversals/{id}/resolve` (posts an explicit ops-supplied `manual_adjustment`, since §8 only says a reversal lands "wherever the funds actually ended up" without a fixed taxonomy). All admin-auth-gated; the inbound webhook route (`POST /webhooks/settlement/{providerName}`) is the first provider-webhook route actually mounted in this codebase — self-verified via signature, same unauthenticated tier as `/admin/login`.
- ✅ **New `internal/settlement` dependencies closed**: `session.Store` gained six exported, non-publishing CAS methods (`TransitionToSettling`/`TransitionToSettled`/`TransitionToSettlementFailed`/`RetryToSettling`/`TransitionToReversed`/`TransitionToReversalResolved` — settlement publishes its own events per the module map, unlike `transitionToPending`); `treasury.Store` gained `GetConfirmedDepositTotal` (sums confirmed deposits regardless of sweep state) and `ReleaseReservation` (the first real caller of `reserved`→`released` anywhere in the codebase — closes §8 rule 5 for settlement's own two terminal states only; `rejected`/`expired` releasing remains an existing Phase-5 gap, not fixed here); `tenant.Store` gained `EffectiveFeeBps`.
- Verified against a live Postgres: happy path settling → webhook-confirmed `settled` with every ledger account balance matching the exact worked-example arithmetic from §6 (100 USDT → 99,000 fiat @ a 990 locked rate → 98,010 tenant payable / 990 fee at 1% — deterministic test numbers, not the doc's illustrative ones, since no real rate provider is live); bucket-1 failover settling on a second provider; bucket-4 immediate `settlement_failed` with the reversal correctly restoring (not zeroing) the tenant liability; webhook signature rejection; webhook replay as a safe no-op.

*Three gaps closed after this phase, all grounded in the actual code rather than assumed away:*
- *Payout destination: `CreateSession` had no way to specify one at all (`Destination` was always `nil` on a first dispatch attempt). Resolved as a per-session, not per-tenant, field (ARCHITECTURE.md §8 "Payout destination") — `corridors.required_destination_fields` + `sessions.payout_destination`, validated at `CreateSession` right after the corridor lookup, carried into `settlements.pending_destination` at `deposit_confirmed`. Migration `000020`.*
- *`treasury.HandleDepositWebhook` now has a mounted route, `POST /webhooks/treasury/busha` (`cmd/server/treasury_handlers.go`) — self-verified via `treasury.VerifyWebhookSignature`, same unauthenticated tier as `/webhooks/settlement/{providerName}`. Static `busha` segment, not a `{providerName}` wildcard, since self-custody deposit detection already runs via watcher polling — Busha is the only real webhook-driven collection path today.*
- *`cmd/server/settlement_test.go` — the HTTP acceptance test settlement was missing, same style as `session_test.go`/`onboarding_test.go`. Drives session creation (including a rejected-then-accepted `payout_destination`) through hold resolution, the deposit event pipeline, and a real `DispatchWorker` into `settlement_failed` (no settlement provider is enabled in test config, so this is the actual production-accurate terminal path today, not a stand-in), then verifies the failed settlement is visible via `GET /admin/settlements` and that both inbound webhook routes are reachable and signature-gated.*

*Still deferred, not fixed: the cross-package eventbus race surfaced while debugging `settlement`'s own test flakiness (`go test ./...` runs each package as a separate process; several independently register only a subset of handlers against the same live `outbox_events` table, so one process's poller can silently "consume" an event meant for another's handler). Never happens in production (`cmd/server` is the only process, with every handler registered) — deliberately left for later rather than fixed as a drive-by.*

## Phase 7 — Notification ✅ complete

Grounding this phase in the actual code (not `ARCHITECTURE.md`'s aspirational module map) surfaced two real gaps closed as part of the build, not assumed away: `internal/compliance` had zero eventbus wiring at all (the module map claims it publishes `compliance.hold_created`; it never did), and every settlement event plus session's own two deposit events carried only `session_id`/`reservation_id` in their payload — never `tenant_id`, which this module needs to resolve a delivery destination without depending on `session.Store`/`settlement.Store`.

- ✅ **`tenant_id` backfilled into every event this phase consumes** — `internal/session/events.go`'s `transitionByReservation` (shared by `session.deposit_detected`/`session.deposit_confirmed`) and `internal/settlement/webhook.go`'s `transitionSettlementAndPublish` (shared by all four settlement events) now include it; `session.created` already had it. This is what keeps `notification`'s only real dependency `tenant.Store` — never `session`/`settlement` directly, a clean "terminal consumer" module boundary matching `ARCHITECTURE.md` §5.
- ✅ **`compliance.hold_created` wired for real** — `compliance.Store` gained a nil-safe `bus`/`SetEventBus` (same convention every other module's bus field uses) and now publishes it, in the same transaction as the case insert, whenever `ScreenTenant`/`ScreenSession` lands a case in the hold queue — never on approve/reject. Payload carries `tenant_id`/`case_type`/`reference_type`/`reference_id`.
- ✅ **`internal/notification`** — the terminal consumer. `RegisterEventHandlers` subscribes individually to all 8 events (`eventbus.Subscribe` has no wildcard support); one shared handler resolves `tenant_id` straight from each event's payload and inserts a `notification_deliveries` row per applicable channel (`ON CONFLICT (aggregate_id, event_type, channel) DO NOTHING`, defensive against a redelivered underlying event). Channel routing is a compiled-in table, not ops-configurable, same convention as `session.SessionTTL`/`settlement.MaxAutoRetryAttempts`: every `session.*`/`settlement.*` event → the owning tenant's webhook (silent no-op if none configured); `settlement.failed`/`settlement.reversed`/`compliance.hold_created` → a single fixed ops-alert email address, never the tenant's.
- ✅ **`DispatchWorker`** (`dispatch.go`) — same "eventbus handler claims a local row, a ticker-driven worker does the real network call" split `settlement.DispatchWorker` established, for the identical reason (`eventbus.Handler` must be a fast, local-DB-only write; an HTTP POST/SMTP call never can be). Webhook send re-fetches the tenant's *current* signing secret at send time (not snapshotted, unlike the destination URL — a rotated secret should apply to the very next retry) and HMAC-signs with the same scheme `treasury`/`settlement` already use for their own inbound webhooks, just outbound here (`internal/notification/webhook.go`'s own copy — this codebase already tolerates each package defining its own rather than sharing one). Fixed backoff schedule (30s, 2m, 10m, 1h, 6h — 5 attempts) before `dead_letter`, a compiled-in constant like `settlement.RetryBackoff`.
- ✅ **Email adapter, genuinely pluggable** (`providers.go`) — `EmailProvider` (`Name`/`IsEnabled`/`Send`) is vendor-agnostic, same shape `settlement.SettlementProvider`/`treasury.CollectionProvider` already establish; `newEmailProvider` selects the implementation by `EmailProviderConfig.Provider` name, so adding a second vendor later is one new file + one switch case, nothing else in the package changes. **Resend is a real, working integration** (`resendProvider`), not a TODO stub like rate/settlement's undecided-vendor adapters — live-verified request/response shape against Resend's documented API, including surfacing their JSON error message (not just a status code) into `last_error` on failure. An empty/unrecognized `Provider` falls back to `stubEmailProvider`, which always reports itself disabled — fails safe, never a startup error. Still disabled by default either way, so a fresh deployment doesn't accidentally start emailing anyone. A disabled provider dead-letters its delivery immediately rather than working through the full backoff ladder first (fails identically every attempt — the static-config equivalent of settlement's bucket-4 "terminal, no retry").
- ✅ **Ops surface** (`ops.go`, `cmd/server/notification_handlers.go`) — `GET /admin/notifications/deliveries?status=dead_letter`, `POST /admin/notifications/deliveries/{id}/retry` (resets `attempt_count` for a fresh run through the backoff schedule), both admin-auth-gated, same shape as settlement's ops routes.
- Verified against a live Postgres: signed webhook delivery end-to-end against a real `httptest.Server` (signature independently recomputed and checked); a tenant with no webhook configured produces zero rows; a disabled email provider dead-letters on the first attempt; the full backoff-to-dead-letter progression (fast-forwarded deterministically in the DB rather than sleeping for real, since the real schedule spans hours); a redelivered underlying event produces exactly one row; `compliance.hold_created` routes to email only, never a tenant webhook; ops-triggered retry resets a dead-lettered row. Extended `internal/compliance`, `internal/session`, `internal/settlement`'s own tests to assert the new `tenant_id` payload field / `compliance.hold_created` publish behavior.
- Found and fixed a real bug during this work, distinct from the already-known cross-package eventbus race: a test helper's `Cleanup()` cancelled its `bus.Run` goroutine's context but didn't wait for it to actually exit, so a dying goroutine from one test could still be polling the shared `outbox_events`/`notification_deliveries` tables when the next test's fresh one started, silently misattributing deliveries to the wrong test's fake tenant config. Fixed by blocking `Cleanup()` on a `done` channel the goroutine closes.

*Deferred, not fixed (pre-existing, not introduced here): the cross-package eventbus race noted in Phase 6 — now also observable via `internal/notification`'s own tests when run alongside other packages, same mechanism, same "never happens in production" reasoning.*

## Phase 9 — Compliance/security hardening (in progress)

Not part of the original build order — surfaced by comparing the actual v2 codebase against the two policy documents in the sibling `payment-engine` repo's `compliance/` folder (`Information-Security-Policy-Sirfi-Payment-Engine.md`, `Cryptographic-Controls-Policy-2Settle-Payment-Engine.md`), which were written against v1 and still describe controls v2 hasn't ported yet. Grouped by what actually blocks reissuing those policies against v2, not by module.

- **Tenant API-key scoping** — `tenant_api_keys` (migration `000006`) had no permission-list or rate-limit-tier column at all; ISP §3 assumes both exist per key. ✅ **Partial**: migration `000028` adds `rate_limit_tier` (`basic`/`standard`/`enterprise`, default `standard`) and `allowed_cidrs`, both consumed by the items below. A per-key **permission list** (scoping a key to a subset of actions) is still open — genuinely separate work from rate-limit tiering, not attempted here.
- ✅ **Rate limiting** — `internal/platform/ratelimit` (in-memory sliding-window-counter limiter, no external store — this runs as a single binary today). `gateway.HMACMiddleware` enforces each tenant API key's `rate_limit_tier` (100/1,000/10,000 req/min — ISP §6) after signature verification. Every public/pre-auth route in `cmd/server/router.go` is IP-rate-limited too, at a limit chosen for that route's own risk profile rather than one blanket number: `publicRouteIPLimit` (20/min) guards `POST /admin/login`, `/portal/register`, `/portal/login`, `/portal/verify` — the "now more urgent" gap this same bullet used to flag; `publicRateLimit` (60/min) guards `GET /rate/{fiatCurrency}` — generous on purpose, since the underlying rate only recomputes every `RATE_CURRENT_RATE_INTERVAL` (default 15m) so no legitimate caller gains anything polling faster; `publicWebhookIPLimit` (120/min) guards the settlement/treasury provider webhooks — set higher because real traffic there comes from a small, fixed set of known provider IPs rather than diverse end-users, and a dropped webhook is costly (a provider may not retry, turning into a missed settlement/deposit confirmation needing manual ops intervention). `ratelimit.Limiter.Run` evicts idle buckets so the key map doesn't grow forever.
- ✅ **IP whitelisting** — `gateway/hmac.go`'s `ipAllowed` checks a key's `allowed_cidrs` (CIDR-aware, `net.ParseCIDR`) after signature verification, same defense-in-depth placement the package's own prior doc comment described. Empty/unset (the default) means no restriction — opt-in per key, nothing to configure for a tenant that doesn't need it.
- ✅ **Security headers** — `gateway.NewRouter`'s `securityHeadersMiddleware` sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a restrictive CSP (`default-src 'none'`), `Cache-Control: no-store`/`Pragma: no-cache`, and (production only) HSTS — wired inside the router itself so every mounted route gets it automatically, current and future. Deliberately doesn't cover `cmd/server`'s dev-only `/docs` route (Swagger UI, CDN-loaded assets, skipped in production anyway) — that's mounted as this router's sibling, never under it. `X-Powered-By` was never set by Go's `net/http` to begin with.
- ✅ **Blanket per-request audit log** — `internal/platform/audit` (migration `000026`, `request_audit_log`) records every request except `/health`: request ID, method/path, a derived action + resource type/ID (heuristic, off the matched chi route pattern), client IP, user agent, a SHA-256 body hash (never the raw body), status code, response time, and tenant/API-key/admin ID where authenticated. Wired as `gateway.NewRouter`'s outermost middleware (ahead of `Recoverer`, so a panic-turned-500 still gets logged) and drained by a buffered-channel background writer (`Logger.Run`, started in `main.go`) so the DB write never blocks the response — ISP §7. `admin_audit_log` is unchanged and still separately covers the human-readable "who approved what" admin trail. Retention enforcement now built — see the retention bullet below.
- ✅ **Deposit-watcher fraud checks** — `internal/treasury/watcher.go`'s `pollOnce` now also applies, per transaction, before ever recording a deposit: **fake-token/wrong-asset filtering** (the transaction's reported asset must match the reservation's `crypto_asset` exactly — catches a native-coin transfer landing on a token-denominated reservation, which a contract-address-scoped provider query alone doesn't), **dust filtering** (`dustThreshold` per chain, ported from v1's fixed values — 0.00001 BTC / 0.0001 ETH / 0.0001 BNB / 0.1 TRX), and **RBF detection** (`blockstreamTx.isRBFEnabled`, BIP125 sequence check — an RBF-signaled Bitcoin transaction needs `max(minConfirmations, 3)` before it's ever treated as confirmed, same floor v1 applied). Zero-confirmation rejection and amount handling were already correct before this pass.
- **Tenant HMAC secret storage** — `tenant_api_keys.hmac_secret_encrypted` is reversibly AES-256-GCM encrypted, not hashed. The crypto policy's stated v1 design was hash-only storage (`SHA256(secretKey)`), implying the expected signature was computed off the hash itself, never a recoverable raw secret. v2's own code comment acknowledges the tradeoff; needs a deliberate policy call (accept the encrypted-at-rest model, or move to the hash-as-key-material scheme) rather than staying an implicit deviation.
- **Key management** — `TenantSecretEncryptionKey` and `HDWalletSeedEncryptionKey` are both plain env vars (`platform/config`), no KMS/HSM, no rotation schedule. This is the crypto policy's own stated "main gap" in v1, now duplicated across two master keys instead of one.
- **Admin SSO/OAuth** — scoped and scheduled as its own item, see Phase 13.
- **End-user authentication surface** — no JWT, OTP, SIWE, or Google Sign-In code exists anywhere in v2; the session/tenant model today is B2B-only (HMAC-authenticated tenants). ISP §4 describes a whole control surface v2 currently has no equivalent of. Needs an explicit scope decision (build it, or descope it from the policy) before the policy can honestly describe v2.
- **Retention enforcement** — ✅ **Partial**: `internal/platform/audit.RetentionJob` now purges `request_audit_log` rows past a 12-month rolling window (`AUDIT_LOG_RETENTION`, default `8760h`), matching ISP §7's "technical audit logs ... retained for 12 months" exactly. The **5-year financial-record window** (payment sessions, settlement data) is deliberately left alone: ISP §7 states it as a *minimum* retention, not a delete-after trigger, and building an active purge job against session/settlement/ledger data on a guessed policy would risk deleting records the business is actually obligated to keep. Needs a real answer from compliance on what "5-year retention" should *do* (archive to cold storage? nothing, ever, short of a data-subject request?) before any code enforces it.
- ✅ **Outbox table cleanup** — `internal/platform/eventbus.CleanupJob` deletes dispatched `outbox_events` rows older than 12 months (`OUTBOX_RETENTION`, default `8760h`) on a daily sweep (`OUTBOX_CLEANUP_INTERVAL`). Operational hygiene, not a compliance window (per this bullet's original framing) — the 12-month figure here is a deliberate choice to match the audit-log window above, not because anything requires it.
- **Ops alert channel** — v2 routes failed-settlement/drift/SLA-breach alerts through `internal/notification`'s email/webhook pipeline, not Telegram as ISP §7 currently documents. Functionally reasonable, but the policy text is now stale against the actual mechanism.
- **Infra-layer controls** (reverse-proxy WAF/`mod_security2`-equivalent, DoS blocking/`mod_evasive`-equivalent, request body size cap, TLS termination, OS patch cadence) — not visible in this repo at all; v1's policy points to Apache config outside the codebase. Needs answering at the deployment layer before either policy can be reissued against v2, per the crypto policy's own §1 commitment to do so once v2 is in production.

*Next: the remaining open items (HMAC secret storage scheme, key management/KMS, end-user-auth scope, the 5-year financial-record retention policy, ops alert channel docs, infra-layer controls) are all policy/business decisions rather than code — need an answer from compliance/ops before any of them can move. Tenant API-key permission-list scoping is the one still-open code item.*

## Phase 10 — Jurisdiction-aware KYB & real screening provider (part 1 ✅ complete, part 2 not started)

Scoped from a walkthrough of `compliance_cases` (migration `000008`): two related gaps in the KYB flow, bundled together since the screening provider needs the same jurisdiction data the required-fields config does. Africa-first scope, per product direction.

- ✅ **Config-driven, per-jurisdiction KYB document requirements** — new `jurisdiction_kyb_requirements` table (migration `000029`), keyed by `fiat_currency` (unique), holding `jurisdiction` (human-readable regulator label) and `required_fields TEXT[]` — same "row not a redeploy" shape as `corridors.required_destination_fields`; no row for a currency means nothing required yet. `internal/compliance/jurisdiction.go`: `UpsertJurisdictionRequirement`/`GetRequiredFields`/`ListJurisdictionRequirements`. Still just `SandboxProvider` registered; every real KYB case defaults to the manual hold queue. Candidates remain **Smile Identity**, **Youverify**, **Prembly (IdentityPass)** — vendor selection is a business decision; the code-side work (`compliance.ScreeningProvider` + `Registry.Register`) is small and additive whenever it's picked, no changes needed to `compliance_cases`/`ScreenTenant`/any existing caller.

New `tenant.Store.GrantCorridorEntitlement(ctx, tenantID, corridorID, feeBpsOverride)` is the gated wrapper: looks up the corridor's fiat currency (`corridor.Store.FiatCurrencyForCorridor`, new), checks `compliance.Store.IsJurisdictionApproved(ctx, tenantID, fiatCurrency)` (new — `EXISTS` query against `compliance_cases` for an approved `kyb` case whose `declared_currencies` covers it), and only then delegates to `SetCorridorEntitlement`. ## Phase 11 — Admin read/browse API surface, for a frontend dashboard (not started)

`cmd/server/router.go`'s `/admin` route group (17 endpoints) was built for ops to *act* — create a tenant, submit KYB, resolve a hold, retry a settlement — one record at a time, driven by curl/scripts. It has almost no way to *browse*. Contrast with `/portal` (Phase 9a), built for a single tenant's self-service and already has a full read surface for its own data: `GET /portal/sessions`, `/portal/settlements`, `/portal/balance`, `/portal/notifications`, `/portal/api-keys`. Nothing analogous exists admin-side across *all* tenants — a dashboard can't be built against this API today. Needed before any frontend work starts:

- **`GET /admin/tenants`** (list) and **`GET /admin/tenants/{id}`** (detail) — missing entirely. `tenant.Store.GetTenant` already exists at the store layer (just never routed), but there's no `ListTenants` method at all — needs pagination and a status filter (`pending_kyb`/`active`/`suspended`/`deleted`) from the start, same reasoning as the outbox/audit-log growth concerns already flagged in Phase 9.
- **`GET /admin/corridors`** (list) and **`GET /admin/corridors/{id}`** (detail) — needed so a frontend can render a corridor picker for the "grant entitlement" action (`POST /admin/tenants/{id}/corridors/{corridorID}`, which today requires already knowing a corridor's UUID). `corridor.Store.GetCorridorByID` exists; `ListCorridors` doesn't.
- **`GET /admin/tenants/{id}/sessions`** and **`GET /admin/sessions/{id}`** — `session.Store.ListSessionsByTenant` and `GetSession` already exist and just need routing. A cross-tenant/global session search (e.g. "find this session by ID without knowing its tenant") is a separate, larger question — worth deferring until the per-tenant view proves insufficient.
- **`admin_audit_log` and `request_audit_log` read paths** — both are write-only today. `adminauth.Store.LogAction` writes `admin_audit_log` but has no corresponding `List`; `internal/platform/audit` writes `request_audit_log` with no read method at all. A dashboard's "who did what" and incident-investigation views depend on both — this needs new store methods, not just new routes, and `request_audit_log` in particular carries client IPs/user agents (ISP §7 territory), so its read endpoint needs its own access consideration, not just the standard admin-auth gate.
- **Pagination/filtering as a first-class concern**, not an afterthought — every list endpoint above sits on a table that only grows (tenants, sessions, both audit logs). Building them unpaginated now just recreates the Phase 9 "accumulates forever" pattern one layer up, at the API rather than the DB.

## Phase 12 — KYB submission becomes portal-only (not started)

Product decision: the tenant submits their own KYB via the portal; admin's role in the KYB flow is review/resolve only (`GET /admin/compliance/holds`, `POST /admin/compliance/holds/{id}/resolve`), never submission on the tenant's behalf. Today both `POST /admin/tenants/{tenantID}/kyb` (`cmd/server/handlers.go`'s `adminHandlers.submitKYB`) and `POST /v2/portal/kyb` (`cmd/server/portal_handlers.go`'s `portalHandlers.submitKYB`) exist side by side, calling the same `compliance.Store.ScreenTenant`.

The complication surfaced while scoping this: `POST /admin/tenants/{tenantID}/kyb` isn't just a redundant alternate path — it's currently the *only* KYB path for a tenant created via `POST /admin/tenants` (`tenant.Store.CreateTenant`), because that endpoint takes no email, so a tenant created that way has no `contact_email` and can't request a portal magic link at all. Only `tenant.Store.RegisterTenant` (the self-service `POST /portal/register` path, Phase 9a) sets `contact_email`.

Resolved shape: `POST /admin/tenants` starts requiring an email, and calls `RegisterTenant` (or an equivalent that sets `contact_email`) instead of the email-less `CreateTenant`. This keeps a real admin-initiated onboarding path (e.g. a negotiated enterprise deal an admin sets up manually) while guaranteeing every tenant, however created, can log into the portal and submit their own KYB — admin creation and KYB submission become fully separate steps, never the same actor. `POST /admin/tenants/{tenantID}/kyb` and `adminHandlers.submitKYB` are then removed entirely, not just deprecated.

Downstream cleanup this touches, so a future implementer isn't surprised by test/doc breakage:
- `cmd/server/onboarding_test.go` — currently posts straight to the admin KYB endpoint; needs reworking to go through `POST /admin/tenants` (now email-requiring) → portal magic-link login → `POST /portal/kyb`, closer to how `cmd/server/portal_test.go` already exercises the self-service flow.
- `docs/TRANSACTION_FLOW.md` — step 2 currently documents `POST /admin/tenants/{tenantID}/kyb` as the canonical onboarding step; needs rewriting to the portal-only flow.
- `docs/openapi.yaml` — drop the `/admin/tenants/{tenantID}/kyb` path entirely.
- `README.md`'s admin-endpoint bullet list — currently lists "tenant onboarding/KYB" under admin-authenticated actions; needs to drop KYB submission specifically (review/resolve stays).
- `CreateTenant` itself (`internal/tenant/tenant.go:120`) likely becomes dead code once `POST /admin/tenants` calls `RegisterTenant` instead — worth checking for other callers before deleting it outright.

## Phase 13 — Admin SSO/OIDC login (not started)

`admin_users` (migration `000003`) is homegrown password storage — bcrypt hash + DB-backed sessions — built as a targeted fix for v1's single-shared-secret finding (see that migration's own comment), not a full IAM solution. Moving staff login to SSO removes password storage from this codebase entirely and centralizes revocation/MFA at the identity provider, which matters more as the admin roster grows past a small founding team. Generic OIDC, not a vendor-specific integration — any OIDC-compliant IdP (Google Workspace, Okta, Azure AD, etc.) should work without code changes, just IdP-side config.

**What changes, what doesn't:**
- `admin_sessions` (the `token_hash` bearer-token table) stays exactly as-is. OIDC is only the authentication step — proving who's logging in — not session management. The same reasoning from the original admin-auth design holds: a DB-backed session gives instant per-admin revocation that a stateless approach can't, so login flowing through an external IdP doesn't change how sessions are issued or checked afterward.
- `admin_users` needs two changes: `password_hash` becomes nullable (an SSO-provisioned admin may never have a password), and a new `oidc_subject TEXT UNIQUE` column — the IdP's stable `sub` claim, not email, is the correct binding per the OIDC spec (email can be reassigned or typo'd at the IdP; `sub` can't).
- Two new unauthenticated-tier routes (same tier as today's `POST /admin/login`): a redirect-to-IdP endpoint and a callback endpoint that exchanges the auth code, verifies the ID token, resolves it to an `admin_users` row by `oidc_subject` (creating one on first login for provisioning, or requiring a pre-existing row, depending on whether self-provisioning or admin-invited-only is the intended flow — open decision), and issues an `admin_sessions` token exactly like `Login` does today.
- `password_hash`-based `POST /admin/login` should stay as a break-glass fallback rather than being deleted outright — a tightly-controlled emergency path (e.g. IdP outage) is standard practice, not a half-measure; just make sure it's not the every-day path once SSO is live.
- Config additions (OIDC issuer URL, client ID/secret) are plain env vars for now, same as the existing `TenantSecretEncryptionKey`/`HDWalletSeedEncryptionKey` pattern — the Phase 9 "Key management" gap about no KMS/rotation applies here too, not a new problem this introduces.
